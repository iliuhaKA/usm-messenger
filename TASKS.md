# USMessenger — Бэклог задач и идей

> Единый документ со всеми задачами по доработке мессенджера: от критичных недостающих фич до «приятных» улучшений и амбициозных идей.
> Каждая задача описана по шаблону: **заголовок → описание → затрагиваемые компоненты → теория/технологии → доп. заметки** (приоритет, сложность, критерии готовности, подводные камни).

## Условные обозначения

- **Приоритет:** `P0` — критично для полноценного мессенджера · `P1` — важно · `P2` — желательно · `P3` — идеи «на вырост»
- **Сложность:** 🟢 низкая · 🟡 средняя · 🔴 высокая

## Текущее состояние (база, от которой отталкиваемся)

**Уже реализовано:** вход по email/IDNP + пароль (JWT 24ч, отзыв через Redis-сессии), чаты GROUP/DIRECT/CHANNEL с ролями, отправка текста и вложений (MongoDB GridFS), real-time доставка через STOMP, индикатор «печатает», presence (online/offline), счётчик непрочитанных, pin/mute чатов, аватары, шифрование сообщений AES-256-GCM, смена пароля и профиля.

**Архитектура:** Spring Boot (Java 21) + React 19/TypeScript/Vite. Polyglot persistence: **PostgreSQL** (сущности), **MongoDB + GridFS** (файлы), **Redis** (presence, typing, unread, JWT-сессии).

> ⚠️ **Решено:** сценарий «первого входа с установкой пароля» (`set-password`) **не реализуем** — пользователям выдаются готовые учётные записи (логин/пароль создаются администратором заранее).

# 🔴 P0 — Критично

## 1. Пагинация сообщений

**Описание.** Сейчас `GET /chats/{chatId}/messages` отдаёт **все** сообщения чата сразу. При накоплении истории это убьёт и сервер, и клиент. Нужна постраничная (cursor-based) подгрузка: при открытии чата грузим последние N сообщений, при скролле вверх — подгружаем более старые.

**Компоненты.**
- **Backend:**
  - `controller/ChatController.java` — добавить query-параметры `?before={messageId|timestamp}&limit=50` в эндпоинт сообщений.
  - `service/MessageService.java` — метод `getMessages(chatId, userId, before, limit)`.
  - `repository/MessageRepository.java` — запрос `findByChatIdAndIdLessThanOrderByIdDesc(..., Pageable)` (keyset/seek-пагинация).
  - `dto/response/MessageResponse.java` — обернуть в ответ с курсором (`hasMore`, `nextCursor`).
- **Frontend:**
  - `api/messages.api.ts` — `fetchMessages(chatId, { before, limit })`.
  - `hooks/useMessages.ts` — перейти на `useInfiniteQuery` (TanStack Query) вместо `useQuery`.
  - `components/chat/MessageList.tsx` — детект скролла вверх + сохранение позиции скролла при подгрузке (anchor).

**Теория и технологии.**
- **Keyset (cursor/seek) пагинация vs OFFSET-пагинация** — почему `OFFSET` плох на больших таблицах (линейная деградация), а seek по индексу `(chat_id, id)` — стабилен.
- Spring Data `Pageable`, `Slice` (Slice не считает total count — дешевле, чем `Page`).
- TanStack Query `useInfiniteQuery`, `getNextPageParam`.
- Сохранение scroll-anchor при добавлении контента сверху (`scrollHeight` до/после).

**Доп.** Приоритет `P0` · Сложность 🟡 · **Готово, когда:** при 1000+ сообщениях чат открывается мгновенно (грузит ~50), скролл вверх плавно подгружает старые без «прыжков». **Подвох:** real-time STOMP-сообщения должны корректно дописываться в кэш `useInfiniteQuery` (первая страница), не ломая курсоры.

## 2. Удаление сообщений

**Описание.** В плане был `DELETE /messages/{id}`, но в коде его нет. Нужно мягкое удаление (soft-delete): автор (или админ чата) удаляет сообщение → у всех оно превращается в «Сообщение удалено». Жёсткое удаление вложения из GridFS — опционально.

**Компоненты.**
- **Backend:**
  - Новый `controller/MessageController.java` (или метод в `ChatController`) — `DELETE /messages/{id}`.
  - `service/MessageService.java` — `deleteMessage(messageId, userId)` с проверкой прав (автор или ADMIN чата).
  - `entity/Message.java` — поле `deletedAt` / `isDeleted` (новая Flyway-миграция `V6__message_soft_delete.sql`).
  - STOMP-broadcast события удаления в `/topic/chats/{id}/messages` (тип события `DELETED`).
- **Frontend:**
  - `api/messages.api.ts` — `deleteMessage(messageId)`.
  - `components/chat/MessageList.tsx` / `MessageItem` — контекстное меню «Удалить», рендер «удалённого» состояния.
  - `components/chat/ChatStompBridge.tsx` — обработка события удаления (убрать/заменить сообщение в кэше).

**Теория и технологии.**
- **Soft-delete паттерн** (флаг вместо физического удаления) — сохранение целостности тредов/ответов.
- Авторизация на уровне сервиса (ownership-check), уже есть похожее в `ChatService.ensureAdmin`.
- Расширение протокола STOMP-сообщений: единый envelope `{ type: CREATED|DELETED|EDITED, payload }`.
- Каскад: что делать со вложением в GridFS (оставить/удалить) и с сообщениями, которые на него ссылались через reply.

**Доп.** Приоритет `P0` · Сложность 🟡 · **Готово, когда:** удаление отражается у всех участников в реальном времени. **Подвох:** нужно решить окно «можно удалить у всех» (например, всегда для автора) и не сломать `replyTo`-ссылки.

## 3. Ответ на сообщение (Reply / цитирование)

**Описание.** Инфраструктура уже частично есть: в `Message` присутствует FK `replyTo`. Нужно довести до рабочей фичи — отправка сообщения с указанием родительского, отображение цитаты-превью над сообщением, клик по цитате → скролл к оригиналу.

**Компоненты.**
- **Backend:**
  - `dto/request/SendMessageRequest.java` — добавить поле `replyToId`.
  - `service/MessageService.java` — заполнять `replyTo` при создании.
  - `dto/response/MessageResponse.java` — вкладывать краткое превью оригинала (`replyToId`, `replyToSenderName`, `replyToPreview`).
  - `mapper`/маппинг ответа.
- **Frontend:**
  - `types/message.types.ts` — поля reply.
  - `components/chat/MessageComposer.tsx` — состояние «отвечаем на…», панелька над инпутом с крестиком.
  - `components/chat/MessageList.tsx` — рендер блока-цитаты внутри бабла + обработчик клика (scroll-to + подсветка).
  - `api/messages.api.ts` — прокинуть `replyToId`.

**Теория и технологии.**
- Self-referencing FK в JPA (`@ManyToOne` на ту же сущность), уже есть в `Message`.
- Денормализация превью в ответе (чтобы не делать доп. запрос к оригиналу на клиенте).
- Программный скролл к DOM-элементу по id (`scrollIntoView`) + временная CSS-подсветка.

**Доп.** Приоритет `P0` · Сложность 🟢 (дешёвая — половина уже есть) · **Высокая отдача.** **Подвох:** оригинал может быть не загружен (вне текущей страницы пагинации) — тогда по клику нужно догрузить контекст.

# 🟡 P1 — Важно

## 4. Поиск по сообщениям

**Описание.** Прямая «боль» аудитории из ТЗ (студенты теряют задания/файлы). Поиск по тексту сообщений: глобальный и/или в рамках чата. Усложнение: сообщения **зашифрованы AES-GCM at rest**, поэтому обычный SQL `LIKE` по `content` не сработает.

**Компоненты.**
- **Backend:**
  - `controller` — `GET /chats/{chatId}/messages/search?q=` и/или `GET /messages/search?q=`.
  - `service/MessageService.java` — логика поиска.
  - `security/MessageCrypto.java` — связано с проблемой шифрования (см. ниже).
  - Возможно отдельная поисковая таблица/индекс.
- **Frontend:**
  - Новый компонент поиска (поле + результаты) в `components/chat/`.
  - `api/messages.api.ts` — `searchMessages`.

**Теория и технологии.**
- ⚠️ **Ключевая дилемма из-за шифрования:**
  - Вариант A — расшифровывать на сервере и фильтровать в памяти (просто, но медленно и не масштабируется).
  - Вариант B — **blind index / searchable encryption**: хранить рядом HMAC-токены слов (детерминированный хэш) для поиска по равенству. Безопаснее full-text, но сложнее.
  - Вариант C — отказаться от шифрования ради PostgreSQL full-text search (`tsvector`, `GIN`-индекс) — компромисс приватность/функциональность.
- **PostgreSQL Full-Text Search**: `to_tsvector`, `to_tsquery`, `GIN`-индексы, ранжирование `ts_rank`.
- Опционально: вынести поиск в **Elasticsearch/OpenSearch** или Postgres-расширение `pg_trgm` для fuzzy-поиска.

**Доп.** Приоритет `P1` · Сложность 🔴 (из-за шифрования) · **Готово, когда:** пользователь находит сообщение по слову и переходит к нему. **Совет:** для курсовой проще всего Вариант A в рамках одного чата + явно описать trade-off в отчёте.

## 5. Редактирование сообщений

**Описание.** В `Message` уже есть поле `updatedAt`, но логики редактирования нет. Автор может отредактировать своё текстовое сообщение; у всех показывается метка «изменено».

**Компоненты.**
- **Backend:**
  - `controller` — `PATCH /messages/{id}` с новым `content`.
  - `service/MessageService.java` — `editMessage(...)`: проверка авторства, перешифровать новый текст, проставить `updatedAt`, broadcast `EDITED` в STOMP.
  - `dto/request` — новый `EditMessageRequest`.
- **Frontend:**
  - `MessageList`/`MessageItem` — пункт меню «Изменить», inline-редактор.
  - `MessageComposer` — режим редактирования (опционально переиспользовать инпут).
  - `ChatStompBridge` — обработка `EDITED`.

**Теория и технологии.**
- Повторное шифрование через `MessageCrypto` (тот же `enc:v1:` формат).
- Единый STOMP-envelope с типами событий (см. задачу №2).
- Метка «(изменено)» = `updatedAt != null && updatedAt != createdAt`.

**Доп.** Приоритет `P1` · Сложность 🟢 · **Подвох:** редактировать можно только текст, не вложение; и стоит ограничить редактирование системных сообщений.

## 6. Refresh-токен (продление сессии)

**Описание.** Сейчас JWT живёт 24ч, `/auth/refresh` из плана не реализован — по истечении пользователя выкидывает. Нужна пара access (короткий) + refresh (длинный) токен, либо «тихое» продление активной сессии.

**Компоненты.**
- **Backend:**
  - `controller/AuthController.java` — `POST /auth/refresh`.
  - `security/JwtTokenProvider.java` — генерация/валидация refresh-токена (отдельный тип/срок).
  - `security/RedisSessionService.java` — хранение refresh-сессий, ротация.
  - `config/SecurityConfig.java` — `/auth/refresh` в публичных.
- **Frontend:**
  - `api/axios.ts` — interceptor на `401`: попытка refresh → повтор запроса; при неудаче — logout.
  - `store/authStore.ts` — хранить и обновлять refresh-токен.

**Теория и технологии.**
- **Access/Refresh token pattern**, ротация refresh-токенов, защита от replay (one-time refresh + хранение в Redis).
- Axios response interceptor, очередь «ожидающих» запросов во время refresh (чтобы не дёрнуть refresh параллельно много раз).
- Решить хранение: refresh в httpOnly-cookie (безопаснее от XSS) vs localStorage.

**Доп.** Приоритет `P1` · Сложность 🟡 · **Подвох:** гонки при параллельных 401 — нужен single-flight refresh.

## 7. Папки для чатов

**Описание.** Заявленная killer-фича для аудитории (структурирование чатов по предметам/группам). В исходной схеме БД были таблицы `folders` и `chat_folders`, но они не реализованы. Пользователь создаёт папки, раскладывает чаты, переключается между ними (вкладки над списком чатов).

**Компоненты.**
- **Backend:**
  - Новые сущности `entity/Folder.java`, связка с чатами (Flyway `V6+`).
  - `repository/FolderRepository.java`.
  - `service/FolderService.java`, `controller/FolderController.java` — CRUD папок, добавление/удаление чата в папку.
  - DTO `request/response` для папок.
- **Frontend:**
  - `api/folders.api.ts` (новый).
  - `components/chat/Sidebar.tsx` — вкладки/табы папок над списком чатов.
  - Новый компонент управления папками (создание/переименование/цвет).
  - `store/` — состояние активной папки.

**Теория и технологии.**
- Моделирование many-to-many (чат ↔ папка) в JPA: `@ManyToMany` или join-сущность.
- Папки **персональны для пользователя** (не глобальны) — FK на `user_id`.
- UI-паттерн вкладок/фильтрации списка (как в Telegram «папки чатов»).

**Доп.** Приоритет `P1` · Сложность 🟡 · **Готово, когда:** пользователь создаёт папку «Матан», кидает туда чаты, фильтрует список по вкладке.

## 8. Админ-панель: управление пользователями и чатами

**Описание.** Нет UI для администрирования. Поскольку учётки выдаются готовыми, нужен инструмент для админа: создавать пользователей, **массово импортировать их (CSV: IDNP/email/ФИО + стартовый пароль)**, создавать чаты и распределять людей по ним.

**Компоненты.**
- **Backend:**
  - `controller/AdminController.java` (новый) — `POST /admin/users`, `POST /admin/users/import` (CSV), `POST /admin/chats` и т.п.; защита `@PreAuthorize`/проверка роли `ADMIN`.
  - `service/` — `AdminService` или расширение `UserService`/`ChatService`.
  - Парсинг CSV, генерация/хэширование стартовых паролей (BCrypt), валидация дублей по IDNP.
- **Frontend:**
  - Новая страница `pages/AdminPage.tsx` + роут (видна только роли ADMIN).
  - `api/admin.api.ts`.
  - Формы создания пользователя/чата, загрузка CSV (drag&drop), таблица пользователей.

**Теория и технологии.**
- **Role-based access control (RBAC)** в Spring Security — method security (`@PreAuthorize("hasRole('ADMIN')")`), уже есть enum `UserRoles`.
- Парсинг CSV на сервере (Apache Commons CSV / OpenCSV), валидация и отчёт об ошибках построчно.
- Защита админ-роутов на фронте (`ProtectedRoute` + проверка роли).
- Идемпотентность импорта (повторная загрузка не плодит дубли).

**Доп.** Приоритет `P1` · Сложность 🔴 · **Подвох:** генерация и безопасная передача стартовых паролей; политика «сменить пароль при первом входе» (можно через флаг `isPasswordSet`, который уже есть в `User`).

## 9. Реакции на сообщения (эмодзи)

**Описание.** В `MessageComposer` кнопка эмодзи уже есть, но disabled. Реакции — это лайки/эмодзи на конкретное сообщение (👍❤️😂), агрегируются по типу с количеством.

**Компоненты.**

  - `repository/MessageReactionRepository.java`.
  - `controller` — `POST/DELETE /messages/{id}/reactions`.
  - `service/MessageService.java` — toggle-реакции, broadcast в STOMP.
  - В `MessageResponse` — агрегированные реакции `[{emoji, count, reactedByMe}]`.
- **Frontend:**
  - `components/chat/MessageList.tsx` — пикер эмодзи по hover/long-press, рендер «чипсов» реакций под сообщением.
  - `ChatStompBridge` — обработка событий реакций.
  - `api/messages.api.ts`.

**Теория и технологии.**
- Уникальный constraint `(message_id, user_id, emoji)` — toggle on/off.
- Агрегация реакций (GROUP BY emoji) — на сервере или на клиенте.
- Real-time обновление через тот же STOMP-канал.
- Библиотека эмодзи-пикера (`emoji-mart` или нативный input).

**Доп.** Приоритет `P1` · Сложность 🟡 · **Готово, когда:** реакция ставится/снимается и мгновенно видна всем.

## 11. Голосовые сообщения

**Описание.** Кнопка записи голоса в `MessageComposer` есть, но disabled. Запись аудио в браузере → загрузка как вложение → проигрывание в чате с волной/таймером.

**Компоненты.**
- **Backend:**
  - Переиспользовать `FileService`/`FileController` (GridFS) — голос как вложение с `type=FILE`/новым типом `VOICE`.
  - Возможно отдельный MIME-handling (`audio/webm`, `audio/ogg`).
- **Frontend:**
  - `components/chat/MessageComposer.tsx` — запись через `MediaRecorder`, таймер, отмена/отправка.
  - `MessageList` — аудиоплеер (нативный `<audio>` или кастомный с waveform).

**Теория и технологии.**
- **Web Audio API / MediaRecorder API**, запрос `getUserMedia({audio:true})`, разрешения браузера.
- Форматы и кодеки (`opus` в `webm`/`ogg`), совместимость браузеров.
- Загрузка Blob как multipart (уже есть инфраструктура вложений).
- Опционально визуализация: `wavesurfer.js`.

**Доп.** Приоритет `P2` · Сложность 🟡 · **Подвох:** Safari/iOS капризен к форматам записи; нужен фолбэк.

## 13. Web Push уведомления

**Описание.** Сейчас только звук при открытом приложении. Нужны браузерные push-уведомления, когда вкладка закрыта/в фоне («не пропускать сообщения по учёбе»).

**Компоненты.**
- **Backend:**
  - Хранение push-подписок (endpoint+ключи) — новая таблица/коллекция.
  - Отправка через **Web Push (VAPID)** при новом сообщении адресатам, у кого чат не замьючен.
  - Учитывать флаг `isMuted` из `ChatMember`.
- **Frontend:**
  - **Service Worker** (новый файл в `public/`) — приём push, показ нотификации.
  - Запрос разрешения, подписка через `PushManager`.
  - `api/` — регистрация подписки.

**Теория и технологии.**
- **Web Push Protocol + VAPID-ключи**, шифрование payload.
- **Service Workers**, `Notification API`, `PushManager`.
- Серверная библиотека (например `web-push` для Node — но тут Java: `java-vapid`/`webpush-java`).
- Жизненный цикл подписки (истечение, обновление).

**Доп.** Приоритет `P2` · Сложность 🔴 · **Подвох:** требует HTTPS, не работает на части iOS-браузеров; нужно чистить «мёртвые» подписки.

## 14. Rate limiting и базовая защита от абьюза

**Описание.** Нет ограничения частоты на логин (брутфорс) и на отправку сообщений (спам/флуд). Добавить лимиты на чувствительные эндпоинты.

**Компоненты.**
- **Backend:**
  - Фильтр/интерсептор или **Bucket4j** поверх Redis (Redis уже в стеке).
  - Применить к `AuthController.login` (по IP/логину) и `MessageService.sendMessage` (по пользователю).
  - `config/SecurityConfig.java` — подключение фильтра.
- **Frontend:**
  - Обработка `429 Too Many Requests` (показ «слишком часто, подождите»).

**Теория и технологии.**
- **Token bucket / leaky bucket** алгоритмы лимитирования.
- **Bucket4j + Redis** для распределённого rate limit.
- HTTP `429`, заголовки `Retry-After`, `X-RateLimit-*`.

**Доп.** Приоритет `P2` · Сложность 🟡.

## 15. Пересылка сообщений (Forward)

**Теория и технологии.**
- Переиспользование вложения без копирования бинарника (share GridFS-id) — экономия места.

**Доп.** Приоритет `P2` · Сложность 🟡.
