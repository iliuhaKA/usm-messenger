## РЕЧЬ

### 1. Актуальность темы (Илья)

Добрый день. Наш проект — **USMchat**, мессенджер, спроектированный специально для коммуникации внутри Молдавского государственного университета.

Проблема, которую мы решаем, знакома каждому студенту и преподавателю: университетское общение сегодня разбросано по множеству платформ — Telegram, Viber, WhatsApp, электронная почта. Учебные чаты смешиваются с личной перепиской, файлы теряются, важные объявления тонут в потоке сообщений. У преподавателей нет единого канала для связи с учебными группами, а у студентов нет удобного способа организовать переписку именно по предметам.

По данным исследований в области образовательных технологий, наличие специализированного инструмента коммуникации повышает вовлечённость студентов и сокращает время на поиск учебной информации. Существующие решения — такие как Microsoft Teams или Moodle — либо перегружены функциями, которые не нужны в контексте молдавского вуза, либо требуют платной инфраструктуры. Мы решили создать лёгкое, целенаправленное решение именно под задачи нашего университета.

### 2. Методология исследования (Мария)

При разработке мы использовали **итеративную методологию** с элементами Agile. Проект разделён на фазы:

- **Фаза 1** — проектирование: анализ целевой аудитории, определение пользовательских сценариев, проектирование схемы базы данных и архитектуры.
- **Фаза 2** — подготовка инфраструктуры: настройка окружения, контейнеризация через Docker, миграции базы данных, конфигурация CORS и безопасности.
- **Фаза 3** — реализация MVP: ядро чатов, авторизация, пользовательский интерфейс, real-time обмен сообщениями.

Мы работали по принципу **разделения ответственности**: Илья отвечал за серверную логику, API, базу данных и интеграцию; я — за дизайн интерфейса, компоненты и пользовательский опыт. Стыковка происходила через заранее согласованные контракты данных — формат JSON-ответов и структуру пропсов компонентов.

### 3. Теоретические аспекты (Илья)

Архитектура USMchat построена на модели **клиент-сервер** с трёхуровневой структурой.

**Серверная часть** реализована на **Java 21** с использованием фреймворка **Spring Boot**. Мы применили паттерн **MVC**: контроллеры принимают HTTP-запросы, сервисный слой содержит бизнес-логику, а слой данных взаимодействует с базой через **Spring Data JPA** и **Hibernate** в роли ORM. Для управления схемой базы данных используется **Flyway** — инструмент версионных миграций, который гарантирует воспроизводимость структуры БД при каждом развёртывании.

База данных — **PostgreSQL**. Схема включает таблицы пользователей, чатов, участников чатов и сообщений с реляционными связями, индексами на часто используемые поля и ограничениями уникальности.

Для обмена сообщениями в реальном времени используется протокол **STOMP** поверх **WebSocket** с транспортом **SockJS** для совместимости с браузерами. Сервер публикует новое сообщение в топик, на который подписаны все участники чата — это обеспечивает мгновенную доставку без необходимости перезагрузки страницы.

Безопасность паролей обеспечивается алгоритмом хеширования **BCrypt**, реализованным через **Spring Security**. В базе данных хранятся только хеши — восстановить исходный пароль невозможно.

**Клиентская часть** построена на **React** с **TypeScript**, что обеспечивает строгую типизацию и снижает количество ошибок. Для управления серверным состоянием используется **TanStack Query** (кеширование, инвалидация, автообновление), а для клиентского — **Zustand**. Стилизация — **Tailwind CSS**, что позволяет быстро создавать адаптивные интерфейсы.

Контейнеризация реализована через **Docker Compose**: три сервиса — PostgreSQL, Spring Boot и фронтенд на Nginx — поднимаются одной командой, что обеспечивает идентичность окружений разработки и развёртывания.

### 4. Практические аспекты (Илья + Мария)

**Илья:**

Покажем работу приложения. Основной пользовательский сценарий:

1. **Авторизация** — пользователь вводит логин (email или IDNP) и пароль. Сервер проверяет учётные данные, сравнивая введённый пароль с BCrypt-хешем в базе. При успехе — возвращается профиль пользователя, при ошибке — код 401 с понятным сообщением.
2. **Список чатов** — после входа в боковой панели отображаются чаты пользователя, разделённые на закреплённые и общие. Для каждого чата показывается последнее сообщение, время и счётчик непрочитанных сообщений. Все данные загружаются через REST API.
3. **Переписка** — при открытии чата загружается лента сообщений. Новые сообщения доставляются через WebSocket в реальном времени. Если собеседник отправил сообщение, оно мгновенно появляется в ленте без перезагрузки, и одновременно приходит звуковое уведомление.
4. **Создание чатов** — через модальное окно можно создать групповой чат, указав название и выбрав участников через поиск по имени.

**Мария:**

Что касается интерфейса — дизайн строился на принципах минимализма и узнаваемости. Мы использовали фирменную зелёную палитру университета. Страница входа — карточка по центру с декоративным фоном. Основной экран — классическая двухколоночная структура мессенджера: сайдбар со списком чатов слева и область переписки справа. Пузыри сообщений стилизованы по направлению: свои — справа зелёные, чужие — слева белые. Поле ввода включает визуальные иконки для будущих функций — голосовых сообщений и вложений.

### 5. Инновационный элемент (Мария)

Инновационность нашего проекта — в том, что это **специализированное решение**, созданное под конкретные потребности университетской среды, а не адаптация универсального мессенджера.

Ключевые отличия:

- **Предзагруженная база пользователей** — администратор загружает список студентов и преподавателей; нет открытой регистрации, что исключает посторонних.
- **Структура чатов по учебным группам и предметам** — типы чатов GROUP, DIRECT и CHANNEL соответствуют реальным сценариям: группа по предмету, личная переписка с преподавателем, канал объявлений факультета.
- **Real-time уведомления через STOMP/WebSocket** — мгновенная доставка сообщений с подсчётом непрочитанных и звуковым оповещением.
- **Контейнеризация** — весь проект разворачивается одной командой `docker compose up`, что упрощает развёртывание на серверах университета.

### 6. Выводы (Илья)

В результате работы мы создали рабочий прототип мессенджера USMchat, который реализует полный пользовательский сценарий: авторизация с хешированием паролей, просмотр и создание чатов, обмен сообщениями в реальном времени с мгновенными уведомлениями и подсчётом непрочитанных.

Проект демонстрирует применение современного стека технологий — Spring Boot, React, PostgreSQL, WebSocket — в контексте реальной задачи. Архитектура разделена на слои, код типизирован, база данных управляется миграциями, а развёртывание автоматизировано через Docker.

### 7. Рекомендации и планы развития (Мария)

В дальнейшем мы планируем развивать USMchat по нескольким направлениям:

- **Безопасность**: внедрение JWT-токенов с refresh-механизмом для полноценной сессионной модели.
- **Загрузка файлов**: возможность отправлять документы, изображения и другие учебные материалы прямо в чат.
- **Профиль пользователя**: страница с персональными настройками, выбором аватара и редактированием данных.
- **Поиск**: полнотекстовый поиск по сообщениям и участникам.
- **Папки для чатов**: организация чатов по категориям — по предметам, семестрам, факультетам.
- **Уведомления**: push-уведомления в браузере и по email для важных сообщений.
- **Мобильная адаптация**: адаптивный интерфейс или отдельное мобильное приложение.

Наша цель — довести USMchat до состояния, в котором его можно будет внедрить в реальную инфраструктуру университета.
